===
## O que é um componente, de fato

Abra `app/posts/posts-board.tsx` e vá até o fim. `Field` é um componente, e é a
ideia inteira em vinte linhas:

```tsx
function Field({ label, name, required, placeholder }: {
  label: string;
  name: string;
  required?: boolean;
  placeholder?: string;
}) {
  return (
    <label className="flex flex-col gap-1 text-sm">
      <span>{label}</span>
      <input name={name} required={required} placeholder={placeholder} />
    </label>
  );
}
```

**Um componente é uma função que devolve marcação.** É isso. O nome começa com
maiúscula para o React distinguir de uma tag HTML comum — `<Field />` é seu,
`<input />` é do navegador.

**Props são os argumentos dele.** Suba um pouco e você vai vê-lo chamado três
vezes:

```tsx
<Field label="Title" name="title" required />
<Field label="Content" name="content" />
<Field label="Author ID" name="authorId" required placeholder="UUID of an existing user" />
```

Cada uma dessas é uma chamada de função. `label="Title"` define o parâmetro
`label`. `required` sozinho significa `required={true}`. O bloco de tipo logo
depois dos parâmetros diz quais props existem e quais são opcionais — o `?` que
você viu na etapa {{step:typescript}}, fazendo o mesmo trabalho aqui.

Três chamadas, uma definição, três campos que não conseguem divergir. É por isso
que você escreve um componente em vez de copiar o bloco `<label>` três vezes.

:::why Chaves são “pare de ser marcação”
Dentro do JSX, `{` significa que a próxima coisa é JavaScript. `{label}` é a
variável. `{isCreating ? 'Creating…' : 'Create product'}` é uma expressão.
Qualquer coisa que você consiga escrever como uma expressão cabe ali — mas não um
`if`, e é por isso que você fica vendo `? :` e `&&` na marcação.
:::

===
## Mais duas coisas que você vai ver em todo lugar

**Renderização condicional.** Não existe `if` dentro do JSX, então uma condição é
uma expressão que resulta ou em algo ou em nada:

```tsx
{createState.error ? <p role="alert">{createState.error}</p> : null}
```

`null` não renderiza nada. Aquela cadeia mais abaixo — `loadError ? … : posts ===
null ? … : posts.length === 0 ? … : …` — são quatro estados de uma lista, em
ordem: falhou, ainda carregando, carregada e vazia, carregada com coisas. Toda
lista que você construir precisa das quatro, e a vazia é a que as pessoas
esquecem.

**Listas e `key`.** Para renderizar muitas coisas você mapeia sobre um array:

```tsx
{posts.map((post) => <li key={post.id}>{post.title}</li>)}
```

`key` é como o React distingue um item de outro entre renderizações. Dê algo
estável e único — um id do banco. Não o índice do array, que muda quando algo é
inserido ou removido, e não nada.

:::note Estado, em uma frase
O `useState` te dá um valor e uma forma de mudá-lo, e mudá-lo re-renderiza o
componente. `const [products, setProducts] = useState(null)` significa: comece em
`null`, e chamar `setProducts(...)` guarda o novo valor e redesenha.
:::

## Conserte

:::why Se você travou no segundo
O `useEffect` recebe dois argumentos: uma função e uma lista de coisas que devem
fazê-la rodar de novo. A lista no final não é pontuação opcional.

Uma lista vazia significa “só depois da primeira renderização”. Nenhuma lista
significa “depois de toda renderização” — e se o efeito muda estado, essa
renderização causa outra, que roda o efeito de novo. Compare a última linha do
efeito com a de `posts-board.tsx`.
:::

===
## O que eram aqueles três

Estes são os três formatos em que um bug de front-end aparece.

| Bug | Onde apareceu | O quanto dói |
| --- | --- | --- |
| `key` faltando | Aviso no console | Nada hoje. Linhas erradas depois de reordenar. |
| Deps do `useEffect` faltando | Aba de rede | Um laço de requisições. Página lenta, servidor martelado. |
| Centavos exibidos como reais | Lugar nenhum | Todo preço errado por cem. |

O último é o tipo perigoso. Sem erro, sem aviso, sem teste falhando. A única
coisa que pega isso é alguém que sabe o que o número significa, olhando a tela.

**Converta onde você exibe, nunca onde você guarda.** Dinheiro é guardado na
menor unidade como número inteiro, porque `0.1 + 0.2` não é `0.3` em ponto
flutuante binário e você não quer isso perto de um total.

E mostre as duas casas decimais, ou `900 / 100` aparece como `9` em vez de
`9.00`:

```tsx
{(product.priceCents / 100).toFixed(2)}
```

=== check=labels,served
## Labels não são decoração

Todo campo vai dentro de um
[`<label>`](https://developer.mozilla.org/pt-BR/docs/Web/HTML/Reference/Elements/label),
como o `Field` faz.

Esse único elemento faz três trabalhos: diz a quem usa leitor de tela para que
serve a caixa, torna o rótulo clicável para focar o campo, e é como o seu teste
do Playwright vai encontrar o campo. Pule e você perde um usuário real e um teste
funcionando ao mesmo tempo.

:::note A ideia do nome acessível
Um leitor de tela anuncia um controle pelo *nome acessível* dele. Um `<label>` dá
um a um campo. O `alt` dá um a uma imagem. O texto de um botão dá um ao botão. Um
botão só de ícone, sem texto, não tem nenhum, e é anunciado como “botão” — e é
por isso que esses precisam de `aria-label`.

Acerte os nomes e use elementos de verdade — `<button>` para um botão, não uma
`<div>` com um manipulador de clique — e você tem a maior parte. O resto está nos
[tutoriais da WAI](https://www.w3.org/WAI/tutorials/), que são curtos e valem uma
tarde.
:::

=== check=e2e-file
## Teste num navegador

O [Vitest](https://vitest.dev/) testa funções. Isto é uma página, então precisa
de um navegador de verdade — isso é o [Playwright](https://playwright.dev/), e
ele mora em `e2e/`.

:::note Por que componentes não têm teste unitário aqui
Renderizar React fora de um navegador significa simular `fetch`, simular módulos
e brigar com renderização assíncrona — engenhoca que te ensina sobre o framework
de testes em vez de sobre o app. E o Next.js não consegue renderizar um Server
Component `async` fora de um navegador, de forma alguma. Um navegador de verdade é
mais fácil de escrever *e* mais próximo do que um usuário faz. O `docs/testing.md`
tem o raciocínio completo.
:::

Crie `e2e/products.spec.ts`, seguindo o modelo de `e2e/posts.spec.ts`:

```typescript
import { expect, test } from '@playwright/test';

test('creates a product from the form', async ({ page }) => {
  const name = `Test mug ${Date.now()}`;

  await page.goto('/products');

  await page.getByLabel('Name').fill(name);
  await page.getByLabel('Price').fill('899');
  await page.getByRole('button', { name: 'Create product' }).click();

  await expect(page.getByRole('heading', { name })).toBeVisible();
});
```

Duas regras evitam a maioria dos testes instáveis:

**Encontre as coisas como uma pessoa encontraria.** [`getByRole`, `getByLabel`,
`getByText`](https://playwright.dev/docs/locators) — nunca classes de CSS. Um
teste que quebra quando alguém muda uma cor é um teste que vai ser apagado.

**Nunca acrescente uma espera fixa.** O `expect(...).toBeVisible()` já espera o
elemento aparecer. Um `waitForTimeout` ou é curto demais — e falha
aleatoriamente num dia lento — ou é longo demais, e toda execução futura paga por
isso.

Mantenha testes de navegador no caminho feliz. Estados vazios e erros de
validação são muito mais baratos de verificar como testes de Route Handler, e uma
suíte grande de navegador fica lenta.

=== attest=e2e-passes
## Rodando

```bash
npm run test:e2e
```

O Playwright sobe o próprio servidor de desenvolvimento na porta 3100, apontando
para o banco de **teste**, e nunca reaproveita aquele em que você está
desenvolvendo, na 3000. Então você pode deixar o app rodando.

:::note Nem sempre foi assim
Isto antes dizia “pare o contêiner primeiro”, porque o Playwright reaproveitava o
que estivesse na porta 3000 — e aquele servidor lê os seus dados de
*desenvolvimento* enquanto as fixtures populam o banco de *teste*. Os testes
falhavam por motivos que não tinham nada a ver com o código.

Uma porta separada resolve isso do único jeito que não dá para esquecer. Isso
vale mais que um aviso mandando as pessoas lembrarem de algo.
:::
