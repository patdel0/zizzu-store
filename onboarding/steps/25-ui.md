**`app/products/products-board.tsx`** — the interactive part. Start from
`app/posts/posts-board.tsx` and adapt it: `'use client'` on the first line, a
`useEffect` that fetches the list on load, a form that posts a new one.

Reading it before you copy it is worth the ten minutes. Three things in there
are not obvious:

- **The `AbortController`.** If you navigate away while a request is in flight,
  the response arrives for a component that is gone. Aborting on unmount stops
  React complaining and stops you leaking work.
- **`useActionState`.** Handles the form submission and gives you `isCreating`
  for free — which is what disables the button so nobody double-submits.
- **The list is updated from the response.** The handler returns the row it
  created, so the new product is added to the list without a second request.

## Labels are not decoration

Every input goes inside a [`<label>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/label), as `Field` does in `posts-board.tsx`.

That single element does three jobs: it tells a screen-reader user what the box
is for, it makes the label clickable to focus the input, and it is how your
Playwright test is going to find the field. Skipping it costs you a real user
and a working test at the same time.

=== check=e2e-file
## Test it in a browser

[Vitest](https://vitest.dev/) tests functions. This is a page, so it needs a real
browser — that is [Playwright](https://playwright.dev/), and it lives in `e2e/`.

:::note Why components are not unit tested here
Rendering React outside a browser means mocking `fetch`, mocking modules, and
fighting asynchronous rendering — a lot of machinery that teaches you about the
test framework rather than about the app. And Next.js cannot render an `async`
Server Component outside a browser at all. A real browser is easier to write
*and* closer to what a user does. `docs/testing.md` has the full reasoning.
:::

Create `e2e/products.spec.ts`, modelled on `e2e/posts.spec.ts`:

```typescript
import { expect, test } from '@playwright/test';

test('creates a product from the form', async ({ page }) => {
  const name = `Test mug ${Date.now()}`;

  await page.goto('/products');

  await page.getByLabel('Name').fill(name);
  await page.getByLabel('Price').fill('899');
  await page.getByRole('button', { name: 'Create product' }).click();

  await expect(page.getByRole('heading', { name })).toBeVisible();
});
```

Two rules prevent most flaky tests:

**Find things the way a person would.** [`getByRole`, `getByLabel`,
`getByText`](https://playwright.dev/docs/locators) —
never CSS classes. A test that breaks when someone changes a colour is a test
that will be deleted.

**Never add a fixed wait.** `expect(...).toBeVisible()` already waits for the
element to appear. A `waitForTimeout` is either too short — and fails at random
on a slow day — or too long, and every future run pays for it.

Keep browser tests on the happy path. Empty states and validation errors are
much cheaper to check as Route Handler tests, and a big browser suite gets slow.

## Running it

```bash
docker compose stop app
npm run test:e2e
```

Stop the container first. Playwright starts its own dev server pointed at the
**test** database, but it will happily reuse whatever is already on port 3000 —
and that one is pointed at your development data.

The first run needs a browser: `npx playwright install chromium`.

When you are done, `./script/server` brings the app back.
