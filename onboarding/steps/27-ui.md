## Fix them

:::why If you are stuck on the second one
`useEffect` takes two arguments: a function, and a list of things that should
make it run again. The list at the end is not optional punctuation.

An empty list means "only after the first render". No list at all means "after
every render" — and if the effect sets state, that render causes another render,
which runs the effect again. Compare the last line of the effect against the one
in `posts-board.tsx`.
:::

## What those three were

These are the three shapes a front-end bug comes in.

| Bug | Where it surfaced | How much it hurts |
| --- | --- | --- |
| Missing `key` | Console warning | Nothing today. Wrong rows after a re-order. |
| Missing `useEffect` deps | Network tab | A request loop. Slow page, hammered server. |
| Cents shown as pounds | Nowhere | Every price wrong by a hundred. |

The last one is the dangerous kind. No error, no
warning, no failing test. The only thing that catches it is somebody who knows
what the number means, looking at the screen.

**Convert where you display, never where you store.** Money is stored in the
smallest unit as a whole number, because `0.1 + 0.2` is not `0.3` in binary
floating point and you do not want that anywhere near a total.

And show both decimal places, or `900 / 100` renders as `9` rather than `9.00`:

```tsx
{(product.priceCents / 100).toFixed(2)}
```

=== check=labels,served
## Labels are not decoration

Every input goes inside a [`<label>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/label), as `Field` does.

That one element does three jobs: it tells a screen-reader user what the box is
for, it makes the label clickable to focus the input, and it is how your
Playwright test is going to find the field. Skip it and you lose a real user and
a working test at the same time.

:::note The accessible-name idea
A screen reader announces a control by its *accessible name*. A `<label>` gives
an input one. `alt` text gives an image one. Button text gives a button one. An
icon-only button with no text has none, and is announced as "button" — which is
why those need `aria-label`.

Get names right and use real elements — `<button>` for a button, not a `<div>`
with a click handler — and you have most of it. The rest is in the
[WAI tutorials](https://www.w3.org/WAI/tutorials/), which are short and worth an
afternoon.
:::

=== check=e2e-file
## Test it in a browser

[Vitest](https://vitest.dev/) tests functions. This is a page, so it needs a real
browser — that is [Playwright](https://playwright.dev/), and it lives in `e2e/`.

:::note Why components are not unit tested here
Rendering React outside a browser means mocking `fetch`, mocking modules, and
fighting asynchronous rendering — machinery that teaches you about the test
framework rather than about the app. And Next.js cannot render an `async` Server
Component outside a browser at all. A real browser is easier to write *and*
closer to what a user does. `docs/testing.md` has the full reasoning.
:::

Create `e2e/products.spec.ts`, modelled on `e2e/posts.spec.ts`:

```typescript
import { expect, test } from '@playwright/test';

test('creates a product from the form', async ({ page }) => {
  const name = `Test mug ${Date.now()}`;

  await page.goto('/products');

  await page.getByLabel('Name').fill(name);
  await page.getByLabel('Price').fill('899');
  await page.getByRole('button', { name: 'Create product' }).click();

  await expect(page.getByRole('heading', { name })).toBeVisible();
});
```

Two rules prevent most flaky tests:

**Find things the way a person would.** [`getByRole`, `getByLabel`,
`getByText`](https://playwright.dev/docs/locators) — never CSS classes. A test
that breaks when someone changes a colour is a test that will be deleted.

**Never add a fixed wait.** `expect(...).toBeVisible()` already waits for the
element to appear. A `waitForTimeout` is either too short — and fails at random
on a slow day — or too long, and every future run pays for it.

Keep browser tests on the happy path. Empty states and validation errors are far
cheaper to check as Route Handler tests, and a big browser suite gets slow.

=== attest=e2e-passes
## Running it

```bash
npm run test:e2e
```

Playwright starts its own dev server on port 3100, pointed at the **test**
database, and never reuses the one you are developing against on 3000. So you
can leave the app running.

:::note It was not always like that
This used to say "stop the container first", because Playwright reused whatever
was on port 3000 — and that server reads your *development* data while the
fixtures seed the *test* database. Tests failed for reasons that had nothing to
do with the code.

A separate port fixes it in the one way that cannot be forgotten. That is worth
more than a note telling people to remember something.
:::
